# v0.1 Release Baseline

- Status: Closed
- Date: 2026-04-20

This document is the operator-facing closure note for Catalyst Continuum `v0.1`.
The detailed release boundary lives in [v0.1-scope.md](v0.1-scope.md).

## Shipped In v0.1

- structured brief intake, validation, and deterministic pack resolution
- durable run, task, artifact, and run-event state in Postgres
- Docker-first runtime-provider execution with enforced task timeouts, applied network-mode settings, explicit restricted-sandbox flags, and best-effort non-root user mapping from the runtime-provider config
- worker control loop plus external-agent claim, heartbeat, and completion flow
- pack-driven repository generation for the baseline service, CLI, and worker packs
- durable artifact pipeline including backlog, dispatch, policy, quality, workspace snapshot, PR candidate, PR export, publication, and GitHub PR artifacts
- HTTP, CLI, and MCP surfaces over the same Rust command layer
- GitHub webhook intake, repository-signal handoff, and draft-PR promotion flow, with GitHub App API publication when outbound App credentials are configured and `gh` fallback only when they are absent
- Redis-backed short-lived coordination for run-scoped promotion locks across CLI, HTTP, and MCP publication requests
- Redis-backed LiteLLM proxy caching for local agent validation traffic
- shared local Postgres persistence for the bundled LiteLLM proxy, with dedicated proxy migrations and state
- LiteLLM OpenTelemetry export into the local collector for gateway traces and semantic log events
- LiteLLM AI edge-gateway boundary, with the orchestrator remaining the source of truth for run policy, runtime control, and publication lineage
- machine-readable AI gateway contract through `config/ai-gateway.yaml` and `describe_instance_config`
- pinned OpenHands launch profiles for host-process versus Docker-sandbox sessions, with repo-local persistence and rendered MCP config
- OpenTelemetry baseline with Collector, Prometheus, Tempo, Loki, and Grafana in the local stack
- external MCP capability-policy contract, upstream `Everything` interoperability checks, and documented `Fetch` guidance
- baseline evaluation coverage through `./scripts/eval-baseline.sh`, including shipped brief validation and one representative promotion-readiness smoke report
- published persisted artifact schemas plus an explicit shared run-event taxonomy registry and schema alignment
- template repository scaffolding for private-instance follow-on work

## Closed v0.1 Local Stack

The shipped local compose baseline for `v0.1` is:

- orchestrator
- worker
- litellm
- postgres
- redis
- otel-collector
- prometheus
- tempo
- loki
- grafana

`LiteLLM` is now a required bundled service in the closed `v0.1` compose baseline.
The local model backend still stays host-run and operator-managed through a pinned `LiteLLM` config.
The repository-standard policy is now explicit: macOS Apple Silicon prefers native `mlx-lm`, while other developer platforms prefer Ollama, and macOS can still opt into Ollama when desired.
The macOS-native examples now use a coding-tuned MLX model by default rather than a general instruct model, and the bundled LiteLLM proxy keeps Redis-backed cache entries in the local stack.
The bundled LiteLLM proxy now also uses the shared local Postgres server through a dedicated LiteLLM database instead of running without persistent proxy state.
The closed `v0.1` boundary also fixes LiteLLM as the AI edge gateway in the architecture. Future search, vector-store, RAG, or A2A-compatible remote-agent edge work should extend that same gateway layer instead of introducing a second mutable control plane beside the Rust orchestrator.
That keeps the compose stack capable of validating real agent traffic without bundling one more model runner image into the control-plane baseline.
The local stack also uses one shared artifact volume between `orchestrator` and `worker`, and the container image carries the baseline `config/runtime-providers.yaml` plus `config/mcp-servers.yaml` so both processes resolve the same instance policy in-container.
The shipped compose baseline now also hardens startup behavior with explicit healthchecks on `prometheus`, `grafana`, and `orchestrator`, and the long-lived `worker` waits for a healthy `orchestrator` before it starts its control loop.
Shared schema bootstrap is serialized with a Postgres advisory transaction lock so cold starts do not race when both `orchestrator` and `worker` initialize the same database.
Containerized live gateway checks use a runtime-local `CATALYST_AI_GATEWAY_STATUS_BASE_URL=http://litellm:4000` override so `GET /ai-gateway/status` probes the in-stack LiteLLM service while the published `ai_gateway` contract can still describe the operator-facing host endpoint.

## Explicitly Not In v0.1

- Proxmox runtime-provider support
- Kubernetes runtime-provider support
- orchestrator-managed third-party MCP sidecar lifecycle
- generic MCP marketplace behavior
- duplication of native agent capabilities such as `git` or local filesystem access

## Validation Baseline

The release baseline should continue to pass these repository-standard checks:

- `./scripts/check-versions.sh`
- `./scripts/ci-compose.sh`
- `./scripts/compose-runtime-check.sh`
- `./scripts/compose-observability-smoke.sh --no-build`
- `./scripts/eval-baseline.sh`
- `./scripts/ci-rust.sh`
- `./scripts/ci-smoke.sh`

On Apple Silicon, `act` remains useful for workflow-shape checks, but full Rust execution under `act` can still hit the known upstream `qemu`/`rustc` crash path.

## Next Scope

The next scoped feature cut is `v0.2`, focused on:

- Proxmox runtime-provider support
- Kubernetes runtime-provider support
- execution isolation hardening around those provider expansions
