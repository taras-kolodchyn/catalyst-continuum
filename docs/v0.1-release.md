## Closed v0.1 Local Stack

The shipped local compose baseline for `v0.1` is:

- orchestrator
- worker
- litellm
- postgres
- redis
- otel-collector
- prometheus
- tempo
- loki
- grafana

`LiteLLM` is now a required bundled service in the closed `v0.1` compose baseline.
The local model backend still stays host-run and operator-managed through a pinned `LiteLLM` config.
The repository-standard policy is now explicit: macOS Apple Silicon prefers native `mlx-lm`, while other developer platforms prefer Ollama, and macOS can still opt into Ollama when desired.
The macOS-native examples now use a coding-tuned MLX model by default rather than a general instruct model, and the bundled LiteLLM proxy keeps Redis-backed cache entries in the local stack.
The bundled LiteLLM proxy now also uses the shared local Postgres server through a dedicated LiteLLM database instead of running without persistent proxy state.
The closed `v0.1` boundary also fixes LiteLLM as the AI edge gateway in the architecture. Future search, vector-store, RAG, or A2A-compatible remote-agent edge work should extend that same gateway layer instead of introducing a second mutable control plane beside the Rust orchestrator.
That keeps the compose stack capable of validating real agent traffic without bundling one more model runner image into the control-plane baseline.
The local stack also uses one shared artifact volume between `orchestrator` and `worker`, and the container image carries the baseline `config/runtime-providers.yaml` plus `config/mcp-servers.yaml` so both processes resolve the same instance policy in-container.
The shipped compose baseline now also hardens startup behavior with explicit healthchecks on `prometheus`, `grafana`, and `orchestrator`, and the long-lived `worker` waits for a healthy `orchestrator` before it starts its control loop.
Shared schema bootstrap is serialized with a Postgres advisory transaction lock so cold starts do not race when both `orchestrator` and `worker` initialize the same database.
Containerized live gateway checks use a runtime-local `CATALYST_AI_GATEWAY_STATUS_BASE_URL=http://litellm:4000` override so `GET /ai-gateway/status` probes the in-stack LiteLLM service while the published `ai_gateway` contract can still describe the operator-facing host endpoint.

## Explicitly Not In v0.1

- Proxmox runtime-provider support
- Kubernetes runtime-provider support
- orchestrator-managed third-party MCP sidecar lifecycle
- generic MCP marketplace behavior
- duplication of native agent capabilities such as `git` or local filesystem access
