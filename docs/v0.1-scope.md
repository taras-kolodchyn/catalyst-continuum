# v0.1 Scope

This document defines the closed cut line for Catalyst Continuum `v0.1`.

`v0.1` is now the final baseline release boundary for the current repository state. The former
`v0.2` contract, interoperability, and operator-ergonomics batch has been pulled forward and
absorbed into this closed `v0.1` cut. The operator-facing closure summary for this cut lives in
[v0.1-release.md](v0.1-release.md).

The rule behind this scope is strict:

- the orchestrator should not duplicate what OpenHands already does well inside a coding session
- the orchestrator should not become a required wrapper around Codex, Cursor, OpenHands, or any
  other native coding-agent UI
- the orchestrator should own control-plane state, policy, runtime control, reproducibility, and
  observability
- LiteLLM can own model and retrieval edge concerns, but it must not become a second mutable source
  of run or policy truth

## Included In Final v0.1 Cut

These are the capabilities that define the final `v0.1` release boundary.

- `Brief intake and validation` Accept a structured brief, validate it, resolve the repository pack,
  and persist a normalized input.

- `Run state model` Represent work as a durable `run` with explicit status transitions, timestamps,
  trigger metadata, resumable state, and a durable event history for auditability.

- `Backlog and task materialization` Generate a deterministic backlog and task graph from the brief
  and pack definition, including priorities, task kinds, and dependencies. The same materialization
  path should also carry an explicit routing contract: supported agents at the pack level,
  brief-level allow/default hints, a pack or brief orchestrator-model hint, and the resolved
  task-level `assigned_agent` output.

- `Artifact pipeline` Track stable artifacts across the run lifecycle, including `backlog`,
  `agent_dispatch_plan`, `policy_report`, `agent_task_report`, generated bundles, workspace
  snapshots, `pr_candidate`, `pr_export`, and publication artifacts.

- `Pack-driven repository generation` Use repository packs as the standard mechanism for template
  selection, runtime contracts, and smoke-test contracts.

- `Controlled Docker runtime` Execute bounded tasks through the runtime provider abstraction with
  Docker as the first substrate. Runtime-declared task timeouts should be enforced, not treated as
  documentation only. Task containers should carry deterministic names and audit labels so timeout
  cleanup can target the container itself, not only the local Docker client process. Runtime
  execution artifacts should also capture stdout and stderr with explicit byte counts and
  truncation markers so noisy agents cannot grow memory, database, or UI payloads without bound.

- `Worker control loop` Provide repeatable run progression through `run next task` and `worker once`
  style control actions. The worker must also recover stale `running` tasks after process loss so a
  run can self-heal without manual database edits. External executors must also have a queue-safe
  claim/heartbeat/complete path for their own assigned tasks, with durable reclaim-lease refresh,
  persisted report artifacts, and the same retry semantics as the worker-managed path.

- `Run inspection` Expose durable run, task, run-event, and artifact inspection through CLI, HTTP,
  and MCP adapters that all reuse the same Rust command layer. Artifact inspection should allow
  agent clients to resolve metadata and inspect the persisted manifest for `backlog`,
  `agent_dispatch_plan`, `policy_report`, `quality_report`, and publication artifacts without
  shelling into the artifact directory manually. Event inspection should expose the same run/task
  transition history to operators and agents without forcing them to reconstruct state from logs.

- `Developer handoff` Package a completed run into a `developer_handoff` artifact that contains a
  human-readable `review.md`, a reusable `agent-review-prompt.md`, and a structured
  `manifest.json`. The handoff must be available through the shared CLI/HTTP/UI command path so a
  solo developer can move from orchestrated execution to Codex, Cursor, OpenHands, or GitHub review
  without rebuilding context manually.

- `Developer session package` Provide an offline-friendly solo-developer entrypoint that turns a
  daily task recipe into `brief.json`, Codex/Cursor/OpenHands prompts, a session manifest, and a
  human runbook. This should give value before a full orchestrator run by standardizing task
  context and validation expectations across coding agents.

- `Developer run entrypoint` Provide a one-command solo-developer path that turns a daily task or an
  existing session `brief.json` into a validated run, submits it to the orchestrator, executes the
  Docker-backed task graph, evaluates policy and quality, exports a local PR candidate, and
  generates the developer handoff without pushing to GitHub. This must reuse the shared CLI command
  layer and leave an inspectable `run-summary.json` plus the normal run artifacts.

- `HTTP liveness and readiness` Expose explicit control-plane liveness and readiness probes for
  operators and automation. Readiness should reflect actual Postgres/schema availability rather than
  a static success payload.

- `GitHub webhook intake and execution` Accept signed GitHub App webhook deliveries through the HTTP
  control-plane surface, validate `X-Hub-Signature-256`, persist structured receipts for audit and
  local debugging, keep a durable inspectable delivery record in Postgres, and attach a normalized
  routing decision that distinguishes ignored probes from safe automation candidates. Candidate
  deliveries should materialize durable control-plane action requests that can be inspected and
  executed through the same shared CLI/HTTP/MCP command layer. The first executor slice in `v0.1` is
  `sync_default_branch` for a signed default-branch `push`: it claims the next pending request,
  persists a request-scoped execution report plus repository-scoped default-branch state, emits a
  durable repository-scoped automation signal for downstream orchestration, records telemetry, and
  marks the request terminal with attempt counts and timestamps. That signal must also support an
  explicit signal-to-run handoff, so an operator or MCP client can validate a brief against the same
  repository context and materialize a run with trigger `repository_signal` without inventing hidden
  automation. The first brief-wired automation composition should also be real in `v0.1`: one
  control-plane step that validates a repository-scoped brief, advances at most one pending webhook
  action, and then materializes the freshest matching repository signal into a run when possible.
  That handoff must reject stale signals once the persisted default-branch state has already
  advanced, so the control plane does not materialize runs against an older observed head. When a
  newer default-branch sync supersedes an older pending automation handoff for the same repository
  branch, the older signal should move to an explicit terminal status instead of lingering in the
  pending queue. Stale `running` action requests should be reclaimed automatically before the next
  claim so a crashed worker cannot wedge repository sync forever. Rich unattended multi-brief
  routing can come later, but signed ingress, durable request state, durable repository signals, a
  real executor path, and one safe brief-driven automation cycle should all be real and testable in
  `v0.1`.

- `Brief-level policy enforcement` Enforce control-plane policy that LiteLLM does not cover: planned
  task count, total timeout budget, bounded retry scheduling, allowed task kinds, allowed runtime
  providers, and allowed sandbox profiles. Persist a `policy_report` artifact on accepted runs and
  re-check task execution against the stored run policy. Expose explicit run policy evaluation
  through the same CLI/HTTP/MCP command layer.

- `Publication gates` Require explicit prerequisite artifacts, valid run state, and an automated run
  quality report before publication or GitHub PR opening steps. Quality evaluation should reject
  stale derived artifacts, not only missing ones. Promotion artifacts should carry explicit lineage
  back to the current passed quality report, not just to the latest PR candidate. Real-repository
  publication should be able to opt into an instance-level repository target allowlist so the
  control plane rejects unapproved GitHub repositories, remotes, base branches, and generated head
  branch prefixes before pushing or opening a draft PR. Operators should be able to select a
  configured `repository_target_id` instead of manually typing a remote URL; the target supplies the
  canonical remote and branch prefix while manual remotes remain explicit allowed overrides for
  smoke or local validation. Human approval for merge stays in GitHub review and branch protection.

- `MCP server for OpenHands` Expose the orchestrator as an MCP tool server for OpenHands via
  `stdio`, with a stable initial tool surface. The surface should include a read-only run guide so
  agents can ask the orchestrator for the current lifecycle stage and next safe action instead of
  inferring that decision from raw task and artifact rows.

- `Explicit agent routing contract` Treat agent delegation as control-plane data, not hidden
  behavior. Packs should declare supported agents and a default orchestrator-model hint, briefs
  should be able to narrow that contract, and validation should reject mismatches early. Backlog
  items and tasks should expose the resolved `assigned_agent` and `orchestrator_model` so OpenHands,
  Codex, and operators can all inspect the same routing decision. Run submission should also persist
  an `agent_dispatch_plan` artifact that groups tasks per assigned agent so external executors can
  consume a stable delegation document instead of deriving routing ad hoc from task lists. Once a
  run exists, external executors should claim only the next runnable task for their assigned agent,
  refresh that task's lease while they are still working, and complete it through a shared
  control-plane path that preserves durable events, retry state, and `agent_task_report` lineage.

- `OpenHands onboarding` Provide a working first-run path for OpenHands, including local Postgres
  bootstrap, a pinned local `LiteLLM` gateway path for host-run model backends, MCP registration,
  and a safe validation task. That first-run path should also be able to narrow the internal
  orchestrator MCP tool surface to a validation-focused allowlist so local coding models do not
  stall on the full control-plane surface during basic integration proofs. Claimed external-agent
  tasks should also have a real prepared workspace handoff plus a completion path that can capture
  successful scaffold or code output from that workspace back into control-plane artifacts. That
  path should be scriptable, covered by the default stateful MCP and executor contract smokes, and
  have an explicit opt-in live OpenHands smoke for environments with a running LiteLLM/local-model
  setup. The default release checks prove the handoff and policy projection deterministically; the
  live smoke proves the pinned OpenHands runtime when the local agent stack is available.

- `Observability baseline` Ship OpenTelemetry from day one for logs, metrics, and traces across the
  orchestrator path. This is not optional for the MVP. The minimum baseline is:

  - OpenTelemetry instrumentation in the orchestrator and worker path
  - an OpenTelemetry Collector in the local stack
  - exported metrics and logs suitable for Prometheus/Loki-style backends
  - Grafana dashboards for run health, task throughput, failures, and latency
  - explicit visibility into promotion-step outcomes, runtime timeouts, and stale task reclaim
    events

- `LiteLLM AI edge gateway boundary` The bundled LiteLLM service is the designated AI edge for model
  routing, proxy caching, persistent gateway state, and gateway telemetry in the closed `v0.1`
  stack. Search, vector-store, and RAG edge capabilities should extend that same LiteLLM boundary
  when adopted, and optional future A2A-compatible remote-agent ingress should also sit there
  instead of becoming another ad hoc service. The Rust orchestrator remains authoritative for
  run/task/artifact state, runtime and sandbox policy, quality gates, external MCP capability
  contracts, and publication lineage.

- `Pinned builds and CI` Keep versions pinned, retain deterministic local/bootstrap behavior, and
  validate the orchestration path in CI and smoke scripts.

## Pulled Forward From Former v0.2 Plan

These features were originally tracked as `v0.2`, but are now part of the final `v0.1` cut.

- `Declarative external MCP server contract` Packs can declare recommended external MCP servers,
  their purpose, and setup hints. The instance keeps a central allowlist in
  `config/mcp-servers.yaml`, scoped by agent, and the control plane resolves
  `pack recommendation × instance allowlist × run agent routing` into one inspectable run-level
  capability contract. That contract is visible through `validate_brief` and persisted into
  `agent_dispatch_plan` so OpenHands, Codex, and operators inspect the same allowed or denied tool
  surface. This remains descriptive and policy-oriented first rather than an orchestrator-managed
  third-party sidecar lifecycle.

- `Reference MCP interoperability checks` Keep local and CI coverage against upstream reference MCP
  servers so compatibility is not inferred only from our own smoke scripts. The first fixture is the
  upstream `Everything` server because it exercises the broadest reference surface for tools,
  resources, and prompts. The pinned reference package version lives in shared version metadata and
  is validated through a dedicated repository script.

- `Documented Fetch integration` Treat upstream `Fetch` as the first recommended external MCP server
  for web retrieval scenarios that are useful to a pack and not already better handled by the
  orchestrator or the agent's native capabilities. Operator guidance stays explicit about pinned
  launch commands, security caveats, and why `Fetch` is documented first without turning it into an
  orchestrator-managed sidecar.

- `Published artifact schemas` Make the key persisted artifact contracts explicit and inspectable.
  The published schema set covers at least `backlog`, `workspace_snapshot`,
  `task_workspace_input`, `agent_dispatch_plan`, `policy_report`, `quality_report`,
  `agent_task_report`, `execution_log`, `pr_candidate`, and `pr_export`.

- `Structured event model hardening` Tighten and document the durable run-event taxonomy so
  operators, MCP clients, and future UIs can reason over the same event contract instead of parsing
  log text.

- `Repository pack contract hardening` Keep turning packs into the canonical source for template
  selection, supported agents, smoke contracts, and external MCP recommendations. Pack docs and
  examples stay aligned with the contract.

- `External MCP capability-policy tests` Keep strong policy-matrix coverage for the resolved
  external MCP contract: allowed intersections, denied intersections, partial agent matches,
  disabled servers, unknown server recommendations, and transport-level inspection stability for the
  structured validation output.

- `Template repository and self-hosted deployment flow` Separate public upstream code from private
  deployment-specific configuration more cleanly while keeping local Docker validation and later
  Proxmox or Kubernetes evolution in view.

- `Deeper GitHub App integration` Expand beyond signed ingress and safe default-branch sync into a
  cleaner repository automation path that still preserves explicit control-plane state and
  publication gates. The first GitHub issue broker slice imports individual issues, offline
  fixtures, or a bounded issue list into native-agent developer sessions, and can rank a bounded
  issue batch into one next recommended session plus an inspectable batch plan. It also supports
  explicit PR packaging strategies: `per-issue` for one PR per task and `batch` for one aggregate
  session that should produce one PR for a related issue set. The closed v0.1 path can execute one
  issue-derived work package through session creation, local run execution, PR export evidence, and
  GitHub issue sync planning. It can optionally continue through repository-target controlled draft
  PR publication and propagate the created PR URL into the issue evidence. It can prepare or apply
  an `in-progress` claim before execution, record a failed execution attempt when the local run does
  not produce review-ready evidence, record a failed draft PR publication attempt after local
  evidence exists, and sync run evidence back to the source issue(s) through an explicit
  dry-run/apply step that comments with branch, commit, PR URL, labels, and optional completed-state
  closure. Later slices should attach that broker to durable queue state and richer run guidance.

- `Basic evaluation coverage` Add a small but real evaluation layer for brief validation, pack
  selection, artifact generation, and safe promotion decisions. In the closed repository baseline,
  this is the explicit `./scripts/eval-baseline.sh` path backed by the shipped example briefs and
  one representative end-to-end smoke report.

## Deferred Beyond v0.1

These are intentionally deferred so the orchestrator does not become a duplicate agent framework.

- `Orchestrator-managed third-party MCP sidecars` Launching and supervising arbitrary external MCP
  servers from the control plane stays deferred until a clear policy, audit, or reproducibility
  benefit outweighs duplicating client-native MCP management.

- `Custom coding agent logic inside the orchestrator` OpenHands remains the coding agent; the
  orchestrator is the control plane.

- `A second chat UX` The orchestrator should not become another conversational coding interface.

- `Deep git workflow duplication` Commit, branch, and PR ergonomics should stay with the agent and
  GitHub-native tools unless a policy reason forces orchestration.

- `Proxmox runtime provider` Important, but after the Docker path is complete and stable.

- `Kubernetes runtime provider` Important, but after the Docker path and provider contract are
  proven.

- `Production MCP proxy deployment` OpenHands recommends proxy-based MCP for stronger reliability,
  but direct `stdio` is the correct integration path for current development and validation.

- `Richer quality and policy rules` Expand the current control-plane checks into configurable
  thresholds, policy packs, richer retries and runtime guards, and more advanced artifact freshness
  rules.

- `Richer pack library` Expand beyond the current baseline packs once the pack contract and artifact
  model are stable enough to support more verticals without churn.

- `Observability hardening` Expand from the shipped baseline into richer dashboards, alerting, and
  cost or budget telemetry.

- `LiteLLM as a second control plane` LiteLLM may keep expanding as the model and retrieval gateway,
  but authoritative run policy, agent routing, runtime control, and PR promotion state stay in the
  orchestrator.

- `Multi-agent orchestration` This matters later, after the single-run state machine, artifact
  model, and runtime controls are trustworthy.
