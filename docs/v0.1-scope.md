# v0.1 Scope

This document defines the current cut line for Catalyst Continuum `v0.1`.

The rule behind this scope is strict:

- the orchestrator should not duplicate what OpenHands already does well inside a coding session
- the orchestrator should own control-plane state, policy, runtime control, reproducibility, and observability

## Now

These are the features we are actively building into `v0.1`.

- `Brief intake and validation`
  Accept a structured brief, validate it, resolve the repository pack, and persist a normalized input.

- `Run state model`
  Represent work as a durable `run` with explicit status transitions, timestamps, trigger metadata, and resumable state.

- `Backlog and task materialization`
  Generate a deterministic backlog and task graph from the brief and pack definition, including priorities, task kinds, and dependencies.

- `Artifact pipeline`
  Track stable artifacts across the run lifecycle, including `backlog`, `policy_report`, generated bundles, workspace snapshots, `pr_candidate`, `pr_export`, and publication artifacts.

- `Pack-driven repository generation`
  Use repository packs as the standard mechanism for template selection, runtime contracts, and smoke-test contracts.

- `Controlled Docker runtime`
  Execute bounded tasks through the runtime provider abstraction with Docker as the first substrate.
  Runtime-declared task timeouts should be enforced, not treated as documentation only.

- `Worker control loop`
  Provide repeatable run progression through `run next task` and `worker once` style control actions.
  The worker must also recover stale `running` tasks after process loss so a run can self-heal without manual database edits.

- `Run inspection`
  Expose durable run, task, and artifact inspection through CLI, HTTP, and MCP adapters that all reuse the same Rust command layer.
  Artifact inspection should allow agent clients to resolve metadata and inspect the persisted manifest for `backlog`, `policy_report`, `quality_report`, and publication artifacts without shelling into the artifact directory manually.

- `HTTP liveness and readiness`
  Expose explicit control-plane liveness and readiness probes for operators and automation.
  Readiness should reflect actual Postgres/schema availability rather than a static success payload.

- `GitHub webhook intake`
  Accept signed GitHub App webhook deliveries through the HTTP control-plane surface, validate `X-Hub-Signature-256`, and persist structured receipts for audit and local debugging.
  Event-to-run automation can come later, but signed ingress should be real and testable in `v0.1`.

- `Brief-level policy enforcement`
  Enforce control-plane policy that LiteLLM does not cover: planned task count, total timeout budget, bounded retry scheduling, allowed task kinds, allowed runtime providers, and allowed sandbox profiles.
  Persist a `policy_report` artifact on accepted runs and re-check task execution against the stored run policy.
  Expose explicit run policy evaluation through the same CLI/HTTP/MCP command layer.

- `Publication gates`
  Require explicit prerequisite artifacts, valid run state, and an automated run quality report before publication or GitHub PR opening steps.
  Quality evaluation should reject stale derived artifacts, not only missing ones.
  Promotion artifacts should carry explicit lineage back to the current passed quality report, not just to the latest PR candidate.
  Human approval for merge stays in GitHub review and branch protection.

- `MCP server for OpenHands`
  Expose the orchestrator as an MCP tool server for OpenHands via `stdio`, with a stable initial tool surface.

- `OpenHands onboarding`
  Provide a working first-run path for OpenHands, including local Postgres bootstrap, MCP registration, and a safe validation task.
  That path should be scriptable and covered by a stateful MCP smoke check, not left as a manual docs-only flow.

- `Observability baseline`
  Ship OpenTelemetry from day one for logs, metrics, and traces across the orchestrator path.
  This is not optional for the MVP.
  The minimum baseline is:
  - OpenTelemetry instrumentation in the orchestrator and worker path
  - an OpenTelemetry Collector in the local stack
  - exported metrics and logs suitable for Prometheus/Loki-style backends
  - Grafana dashboards for run health, task throughput, failures, and latency
  - explicit visibility into promotion-step outcomes, runtime timeouts, and stale task reclaim events

- `Pinned builds and CI`
  Keep versions pinned, retain deterministic local/bootstrap behavior, and validate the orchestration path in CI and smoke scripts.

## Next

These are the next features to build immediately after the `v0.1` cut is stable.

- `Richer quality and policy rules`
  Expand the initial policy and quality layers into configurable thresholds, policy packs, retries/runtime guards, and richer artifact freshness guarantees.

- `Richer pack library`
  Expand beyond the initial packs once the pack contract and artifact model are stable.

- `Template repository and self-hosted deployment flow`
  Separate public upstream code from private deployment-specific configuration.

- `GitHub App integration`
  Expand from signed webhook intake into cleaner repository automation, event routing, and deeper GitHub App control-plane behavior once the core model is solid.

- `Observability hardening`
  Expand from the MVP baseline into richer dashboards, alerting, and cost/budget telemetry.

## Later

These are intentionally deferred so the orchestrator does not become a duplicate agent framework.

- `Custom coding agent logic inside the orchestrator`
  OpenHands remains the coding agent; the orchestrator is the control plane.

- `A second chat UX`
  The orchestrator should not become another conversational coding interface.

- `Deep git workflow duplication`
  Commit, branch, and PR ergonomics should stay with the agent and GitHub-native tools unless a policy reason forces orchestration.

- `Proxmox runtime provider`
  Important, but after the Docker path is complete and stable.

- `Kubernetes runtime provider`
  Important, but after the Docker path and provider contract are proven.

- `Production MCP proxy deployment`
  OpenHands recommends proxy-based MCP for stronger reliability, but direct `stdio` is the correct integration path for current development and validation.

- `Multi-agent orchestration`
  This matters later, after the single-run state machine, artifact model, and runtime controls are trustworthy.
